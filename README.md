# Mechworks

Мод для Vintage Story 1.22.x. Цель — механические контрапции в духе Create:
блоки, которые двигают другие блоки, питаясь механической энергией.

Текущее состояние: работает на 1.22.7. Поршень, верёвочный подъёмник и
поворотная платформа питаются от ванильной мехэнергии, переносят блоки, везут
стоящего сверху и отодвигают оказавшегося на пути. Склеенные блоки двигаются группой. Направление
задаёт сторона вращения вала; у поршня дальность определяется числом
загруженных балок.

## Сборка

```powershell
dotnet build mechworks.csproj
```

Требуется:

- .NET 10 SDK
- переменная окружения `VINTAGE_STORY` с путём к папке игры
  (здесь: `S:\Users\zhenya\AppData\Roaming\Vintagestory`)

Если переменной нет — можно передать путь напрямую:

```powershell
dotnet build mechworks.csproj -p:VintagestoryDir="S:\...\Vintagestory"
```

После сборки мод автоматически раскладывается распакованной папкой в
`%APPDATA%\VintagestoryData\Mods\mechworks`, отдельно паковать zip не нужно.
Путь переопределяется через `-p:ModDeployDir=...`.

### Энергия

Своей сети энергии нет и пока не нужно. Поршень вешает на себя ванильное
поведение `MPConsumer` прямо из JSON:

```json
entityBehaviors: [{ name: "MPConsumer", properties: { resistance: 0.3 } }]
```

Класс `BEBehaviorMPConsumer` регистрируется самим VSSurvivalMod, поэтому
достаточно ссылки на `VSSurvivalMod.dll`. В коде скорость читается как
`GetBehavior<BEBehaviorMPConsumer>().TrueSpeed`.

Три условия, все выясненные на практике. Первые два роняют игру, третье делает
блок невидимым:

1. **`mechPartShape: null`** в свойствах поведения. Иначе `MPConsumer` берёт форму
   самого блока и отдаёт её рендереру вращающихся частей, который простой куб не
   переваривает.
2. **Блок обязан наследоваться от `BlockMPBase`.** Одного поведения мало.
   `BEBehaviorMPBase.spreadTo` проверяет на null поведение, но разыменовывает
   результат приведения *блока* к `IMechanicalPowerBlock` — блок без интерфейса
   роняет клиент при подведении оси.
3. **Блок надо рисовать самому.** `BEBehaviorMPConsumer.OnTesselation` возвращает
   `true`, не добавив меша: он заявляет, что отрисовку взял на себя сетевой
   рендерер вращающихся частей. Для ванильных машин это правда, но мы от того
   рендерера отказались первым пунктом — и блок не рисует никто. Симптом:
   блок физически есть, выделяется контуром, но невидим. Отсюда
   `BEMoverBase.TesselateSelf`.

Вал подключается к **боковой** грани — спереди и сзади нельзя, там ходит балка.
Какой из двух боков выбран, то и решает, выдвигается поршень или втягивается:
питание слева и справа даёт противоположный смысл вращения. Это единственный
реверс, который вообще доступен в ванили.

Следствие: поршень работает от любого ванильного источника — ветряка,
водяного колеса — через обычные оси и шестерни.

Чего в ванильной сети нет: понятия нагрузки/лимита мощности (stress capacity,
overstress из Create). Если это понадобится — придётся писать свою сеть,
как это сделал Vintage Kinematics.

### Перемещение блоков

Поршень двигает **прямую цепочку** блоков по своей оси, до `MaxPushedBlocks`
(сейчас 12). Всё, что приклеено к этой цепочке, едет вместе с ней — см. «Клей».

`BEPiston.CollectPushChain()` идёт вперёд **от конца балки** и останавливается на
первой свободной клетке — туда цепочка и сдвинется. Отказ (ничего не меняется), если:

- перед балкой сразу пусто — двигать нечего, но балка всё равно выдвигается:
  она часть механизма, а не груз;
- в цепочке недвигаемый блок;
- цепочка длиннее лимита;
- путь уходит в незагруженный чанк (`GetChunkAtBlockPos == null`). Без этой
  проверки `GetBlock` вернул бы там воздух, и запись потерялась бы при реальной
  загрузке чанка.

Блок можно пометить недвигаемым из JSON:

```json
attributes: { mechworksImmovable: true }
```

## Машины

Общее — в `BEMoverBase`: чтение сети, накопление хода, передача клеток энтити,
проверки «что можно двигать». Наследнику остаётся один метод `TryMove()`,
который решает **что** и **куда**.

### Поршень

Выдвигает балку и толкает ей всё, что перед ней; при обратном вращении втягивает.
Вал сбоку, балка ходит по оси варианта блока.

**Дальность задаётся балками.** Правый клик ванильной опорной балкой загружает её
в машину, до `MaxBeams` (4). Одна остаётся внутри противовесом, поэтому полная
загрузка даёт вылет на три клетки:

```csharp
public int Reach => Math.Max(0, beams - CounterweightBeams);
```

Загрузка требует свободной клетки **сзади** — балка физически туда уходит.
Втягивание тоже: это правило самой балки, а не только загрузки.

Балка в мире — настоящие блоки `mechworks:pistonbeam`, спереди и сзади. Это
решение продиктовано требованиями: коллизии, запрет застройки и отрисовку
движок даёт блокам бесплатно, а виртуальной балке всё пришлось бы писать руками.
Игрок их сломать не может (вето через `CanPlaceOrBreakBlock`, потому что
прочность блока в творческом режиме не работает); выходят они разгрузкой
втянутого поршня или сломом машины, и возвращается ровно та порода, что зашла.

Поршень не правит клетки по одной, а **переписывает раскладку из своих
счётчиков** — отсюда самовосстановление после перезагрузки чанка.

#### Анимация хода

Модель поршня — корпус с обручами, гнёзда под вал по бокам, плита на конце
штока. Плита и по одной клетке балки на каждом конце исключены из статического
меша и рисуются `PistonHeadRenderer` со сдвигом.

Три вещи, каждая стоила отдельной итерации:

- **Плита едет на конце балки**, а не на корпусе: усилие идёт вал → корпус →
  балка → плита → груз, так что встречает груз именно плита.
- **Анимировать надо оба конца.** У однородного стержня середина выглядит
  одинаково до и после сдвига, меняются только концы — но их два, а не один.
- **Концы хотят противоположного времени записи в мир.** Клетка, куда стержень
  приходит, должна оставаться пустой до конца хода, иначе блок обгоняет свою
  анимацию. Клетка, откуда уходит, должна освобождаться сразу, иначе отрезку
  неоткуда выезжать. Отсюда `SyncBeamBlocksForStroke`: очистить сейчас, занять
  по прибытии.

Время хода берётся из отметки `strokeStartMs`, а не из счётчика в тике: тик идёт
четыре раза в секунду, а ход длится 0.4 с. И запускает ход **только сервер** —
клиент начинает анимацию, когда узнаёт о смене выдвижения, тем же пакетом, что
приносит энтити с грузом. Иначе два независимых счётчика расходились по фазе на
четверть секунды.

### Поворотная платформа

Поворачивает на четверть за ход всё, что склеено сверху, вокруг своей
вертикальной оси. Четверть — наименьший шаг, при котором все блоки снова
ложатся в сетку; мельче не бывает статичного положения.

Вал подключается сверху или снизу, и выбор торца задаёт направление — как выбор
бока у поршня. Вариантов у блока нет: он симметричен относительно своей оси.

Первая машина, где блоки едут **не на общий вектор**, а каждый в свою клетку.
Поэтому `BlockSnapshot` научился повороту, а общий переносчик — углу: при
повороте источник и цель совпадают с центром вращения, груз никуда не едет, а
рендерер крутит меш вокруг середины этой клетки за время хода.

Благодаря общему пути платформа даром получила синхронизацию слепка с клиентом,
переезд меток клея вместе с блоками и аварийное восстановление, если переносчик
умрёт на полпути.

**Угол размещения и угол проката — разные числа.** `Rotate` и
`GetRotatedBlockCode` получают угол как есть (270 — их общее соглашение), а
анимация берёт кратчайший знаковый эквивалент, то есть −90. Иначе груз едет три
четверти оборота, чтобы попасть туда, куда есть четверть пути. Одно другому не
мешает: они отличаются на полный оборот.

Кстати, `Rotate(θ)` соответствует матричному `RotateY(−θ)` — отсюда минус в
рендерере.

#### Катание по дуге

Опорные проверки требуют **осевых** боксов, а у поворачивающегося груза их нет.
Вместо того чтобы переписывать путь столкновений под произвольно ориентированные
боксы, поворачиваем **пассажира в систему координат груза** (`ToLoadFrame`):
боксы остаются неповёрнутыми, пассажир приходит к ним, и все выверенные допуски
работают без изменений. Один поворот вектора вместо новой геометрии.

Само катание устроено симметрично прямому ходу: скользящий груз сдвигает
пассажира на **расстояние**, пройденное с прошлой обработки, поворачивающийся —
на **угол**. Оба отсчитываются от собственной отметки пассажира, поэтому
результат не зависит от порядка тиков и физики.

Поиск пассажиров при повороте идёт по **заметаемому кругу**: боксы описывают
раскладку при нуле градусов, а пассажир может оказаться с любой стороны оси.

Взгляд поворачивается вместе с позицией, на тот же угол: yaw пользуется той же
угловой конвенцией, где направление это `(cos t, −sin t)`, а `TurnAbout(+d)`
переводит `t` в `t + d`.

А вот **куда** его прикладывать — не выводится. У локального игрока `Pos.Yaw` не
источник, а следствие: камера идёт от накопленного `IInputAPI.MouseYaw`, и
`Pos.Yaw` переписывается из него каждый кадр, так что добавка туда молча
теряется. Своему игроку правим `MouseYaw`, чужой сущности — `Pos.Yaw`
(`SwingView`). Та же по форме развилка, что и с позицией.

Угол **прибавляется**, а не присваивается, — складывается с движением мыши, а не
спорит с ним.

**Позиция и код блока обязаны поворачиваться в одну сторону**, иначе конструкция
сохранит форму, но лестницы в ней будут смотреть не туда. Соглашение взято из
ванили: `BlockBehaviorHorizontalOrientable` шагает назад по
`HORIZONTALS_ANGLEORDER` (E, N, W, S), значит 90° это по часовой сверху, то есть
`(x, z) → (−z, x)` в мировых осях. Сам код блока поворачивает штатный
`Block.GetRotatedBlockCode`.

А вот какой **смысл вращения вала** какому углу соответствует — не выводится:
это стык двух независимых соглашений, и пара подбиралась наблюдением.

Известные дыры:

- **Дуга не проверяется**, только конечные клетки. Блок на краю проходит над
  своей диагональю, и она не тестируется — конструкцию можно провернуть сквозь
  препятствие, стоящее по диагонали.
- **Выталкивание при повороте не работает.** Отдельного условия нет: у поворота
  `TravelDirection` нулевой, и `TryPushOut` отказывается сам. Кого задело дугой,
  тот останется стоять.

### Верёвочный подъёмник

Опускает верёвку до `MaxRopeLength` (24) клеток вниз, находит первый висящий на
ней блок и двигает его на клетку за ход. Направление задаёт сторона вращения
вала, правый клик переворачивает вручную (отладочный рычаг).

Здесь важно, что вертикальной **энергии** не потребовалось. Ванильный
`MPConsumer` знает только четыре горизонтали, но вал подходит сбоку, как у
поршня, — вертикально движется только груз. Ограничение, из-за которого
вертикаль откладывалась, оказалось несущественным при другой форме блока.

Слой энтити для вертикали менять не пришлось вообще: `TravelDirection`, катание
и выталкивание считаются от `SourceOrigin → DestOrigin` и оси Y не различают.

### Клей

Склеенные блоки, которые соприкасаются, двигаются как одно целое. Предмет
`mechworks:glue`: правый клик клеит, повторный снимает.

**Где живут метки.** У блоков VS нет метаданных на позицию без блок-энтити, а
заменять ванильные блоки при склейке нельзя. Поэтому метки лежат отдельно —
`GlueRegistry`, множество позиций, сохраняется вместе с миром через
`SaveGame.StoreData`.

**Только на сервере.** Группа считается внутри `TryMove`, которая и так
серверная, а клиент получает готовый слепок. Клиенту знать про клей незачем,
поэтому ничего не синхронизируется.

**Правило распространения.** Блок присоединяется к группе, только если склеены
**оба** — и он, и сосед. Отсюда следствие: несклеенный груз ведёт себя ровно как
до появления клея, старое поведение сохранено по построению.

**Метки переезжают с блоками.** Снимаются при захвате, кладутся в слепок,
восстанавливаются там же, где приземлились блоки — включая аварийную посадку.
Иначе клей был бы одноразовым: платформа доехала бы до соседней клетки и
рассыпалась.

**Мусорные метки убираются лениво.** Событие `DidBreakBlock` покрывает обычный
слом, но взрывы, распад и генерация мира события не дают. Поэтому метка
проверяется по факту обращения — в подсветке и при сборе группы. Это не
косметика: осиротевшая метка **заклинивала машину**, потому что клетка проходила
проверку «склеена», а потом падала на «блок недвигаемый». Теперь два случая
различаются: блока нет — метка мусорная, идём дальше; блок есть, но недвигаемый —
отказ.

Лимит группы — `MaxGroupSize` (64). Превышение, склейка с недвигаемым и выход за
границу загруженных чанков означают, что машина просто не срабатывает.

#### Подсветка

`GlueHighlighter` раз в 500 мс подсвечивает склеенное в радиусе 24 тому, у кого
клей в руке. `HighlightBlocks` объявлен на `IWorldAccessor`, поэтому сервер
отправляет оверлей игроку напрямую — свой сетевой канал не нужен.

Две грабли, обе стоили итерации:

- **`EnumHighlightShape.Arbitrary`, не `Cube`.** `Cube` в единственном числе —
  это ОДНА коробка, заданная парой углов «от» и «до». Список ровно из двух
  позиций читался как пара углов: один блок подсвечивался, три и больше
  подсвечивались, ровно два — нет.
- **`firstEvent` в `OnHeldInteractStart`.** Обработчик вызывается не только на
  первом нажатии. Без проверки долгое нажатие переключает метку дважды и тихо
  отменяет само себя.

### Плавное движение

Цепочка не телепортируется. `BEPiston.TryPush()` вынимает её из сетки и отдаёт
энтити, которая переносит её в соседнюю клетку за `MoveDurationSec` и кладёт
обратно:

```
BEPiston.TryPush()
  ├─ BlockSnapshot.Capture()        коды блоков + деревья блок-энтити
  ├─ BlockSnapshot.ClearFromWorld() цепочки в мире больше нет
  └─ SpawnEntity(EntityMovingBlocks)
        ├─ OnGameTick: Pos = lerp(source → dest)
        ├─ MovingBlocksRenderer рисует слепок на клиенте
        └─ Settle(): BlockSnapshot.RestoreToWorld() + Die()
```

**Пока энтити летит, блоков в мире не существует.** Если она умрёт не долетев
(выгрузка чанка, `/killallentities`), они пропадут навсегда — поэтому
`OnEntityDespawn` кладёт слепок обратно: до половины пути в источник, после — в
цель. `movingUntil` в поршне не даёт выстрелить повторно, пока ход в воздухе.

Неочевидная деталь восстановления: в сохранённом дереве лежат старые координаты
`posx/posy/posz`, и `SetBlock` их не исправляет. Их надо переписать вручную,
иначе блок-энтити продолжает считать, что находится на прежнем месте. Причём
`posy` пишется из `pos.InternalY`, а не `pos.Y` — `Y` это координата внутри
измерения, сквозная именно `InternalY`.

#### Рендер

Меш собирается один раз при появлении энтити (слепок в полёте не меняется).
Обвязка отрисовки хрупкая, и все три ошибки в ней были найдены только в игре:

- сэмплер называется **`"tex"`**, не `tex2d`;
- нужен `GlDisableCullFace()`, иначе часть граней пропадает;
- `GlToggleBlend(true)`, не `false`.

Тип энтити использует shape с пустым `elements` — штатный рендерер рисует
ничего, всё делает `MovingBlocksRenderer`. Приём из VK.

### Катание

Кто стоит на цепочке — едет с ней. Реализовано в `EntityMovingBlocks`, четыре
условия, каждое выяснено отладкой в игре:

**1. Правку применять после физики.** `rider.AfterPhysicsTick += hook`, не
`OnGameTick`. В обратном порядке гравитация отменяет коррекцию тем же тиком.

**2. Каждую сущность двигает ровно одна сторона.** Клиент — только своего
игрока, сервер — всех остальных (`CanCarry`). Если дельту прибавляют обе,
пассажир уезжает вдвое дальше. В мультиплеере чужого игрока везёт его клиент.

**3. Возвращать опору под ноги.** Пока цепочка в воздухе, её нет в сетке — под
пассажиром дыра. После сдвига он поднимается на поверхность, гасится падение
вниз и физике сообщается, что это земля:

```csharp
double correction = surfaceY - riderBox.Y1;   // не Pos.Y = surfaceY:
if (correction >= 1e-6) rider.Pos.Y += correction;  // позиция ≠ низ бокса
rider.CollidedVertically = true;               // иначе физика продолжает
rider.OnGround = true;                         // разгонять вниз
rider.PositionBeforeFalling.Set(...);          // иначе копится урон от падения
```

**4. Допуски на захват и на удержание разные, по обеим осям.**

| | подобрать | удержать своего |
|---|---|---|
| просел ниже | 0,35 | 1,5 |
| завис выше | 0,0156 | 0,5 |

Захват щедрый, потому что просадка в начале **каждого** хода неустранима: блоки
убирает сервер, а энтити приезжает на клиент отдельным пакетом тиком-другим
позже, и в этом окне игрок падает без пола. Измерено 0,10–0,13, взято 0,35.

Допуск «завис выше» нужен для подъёмника: поднимающаяся платформа каждый тик
подталкивает пассажира вверх, и жёсткие 0,0156 он не переживает.

**5. Две памяти, а не одна.** Их легко перепутать, но вопросы разные:

| | Окно | Зачем |
|---|---|---|
| `SupportGraceMs` | 350 мс | продолжать везти при подскоках ходьбы |
| `RiderMemoryMs` | 3000 мс | «свой пассажир» → мягкие допуски |

Память живёт в `RiderMemory` на мод-системе, **не** внутри энтити: энтити
создаётся заново на каждый ход, а подъёмник делает их десятками подряд. Внутри
энтити память умирала каждый ход, и каждый ход начинался с холодного захвата.

**6. Приземление — отдельная фаза.** `SnapRidersToLanding()` усаживает
пассажиров на поверхность там, где блоки **приземлятся**, до того как отпустить
их. Иначе восстановленный блок появляется с крошечным перекрытием ног игрока,
штатное разрешение коллизий выбрасывает его из блока — на целую клетку вверх и с
положительной скоростью, — и он падает уже оттуда. У Vintage Kinematics это
`SnapSupportedEntitiesToRestoredBlocks`.

Дельта считается не «за тик», а от позиции носителя на момент прошлой обработки
*этого* пассажира — тогда результат не зависит от того, как переплетутся тики и
физика.

#### Почему нет interpolateposition

В типе энтити поведение `interpolateposition` **намеренно отсутствует**. Позиция
— чистая функция от `Progress`, обе стороны считают её одинаково. Поведение же
тянет `Pos` к сетевой `ServerPos`, которую здесь никто не обновляет, и затирает
лерп: блоки оказываются в случайном месте, пассажир теряет опору и проваливается.

#### Отладка

`DebugCarry` печатает высоту ступней, расстояние до ближайшей поверхности,
скорость по Y, направление и выбранный допуск. Включать, когда катание ведёт
себя странно — рассуждениями со стороны это не ловится, проверено многократно.

Читать внимательно **знак** `nearestTopDelta`: отрицательный — пассажир просел,
положительный — его подбросило. Это принципиально разные причины, и лечатся они
в разных местах.

### Выталкивание

Кто оказался на пути — отодвигается передней гранью. Ветка в том же хуке:

```
стоит сверху    → везём
стоит на пути   → выталкиваем
ни то ни другое → отпускаем
```

Вытолкнутого **не везём дополнительно** — его уже двигает передняя грань,
катание сверху дало бы двойное смещение.

Направление известно заранее (`SourceOrigin → DestOrigin`), поэтому расчёт
короткий: вытолкнуть за переднюю грань самого глубокого из задетых блоков,
очистив его, очищаем и остальные. Vintage Kinematics здесь заметно сложнее
(`GetEntryAwarePush` плюс до четырёх итераций), потому что их контрапция ездит
в любом направлении и войти в неё можно с любой стороны.

Обязательные детали, взятые у них:

- **гасить встречный импульс**, иначе выталкиваемый вжимается обратно;
- **ставить `CollidedHorizontally` / `CollidedVertically`**, чтобы физика знала
  о столкновении;
- **оставлять зазор**, иначе следующий тик снова засчитает пересечение.

#### Упор в стену

Выталкивание ограничено свободным местом — иначе игрока между цепочкой и стеной
вдавливало внутрь блоков. `ClampToFreeSpace` бисекцией за шесть шагов ищет
наибольшее смещение, при котором штатный `CollisionTester.IsColliding` ещё не
видит столкновения с миром.

Итог: **прижимает вплотную**, а не вдавливает. Цепочка при этом визуально
наезжает на игрока — деваться ей некуда.

Полным решением было бы заглядывание вперёд: поршень при захвате проверяет,
можно ли будет всех вытолкнуть, и не срабатывает, если нет. Тогда игрок в тупике
просто останавливает машину. Не сделано — сначала надо понять, насколько часто
это всплывает в игре.

## Чего сознательно нет

- **Втягивания.** Поршень только толкает. Из-за этого он одноразовый: толкнул —
  и дальше руками. Циклических машин (ворота, челнок, подъёмник) без втягивания
  не собрать, и вся работа по катанию отыгрывается только наполовину.
- **Проверки заявок (land claims).** Поршень работает автоматически, игрока
  рядом может не быть. Перед мультиплеером нужно добавить проверку вида
  `World.Claims.TryAccess(...)` — иначе мод сможет ломать чужие постройки.
- **Вертикального поршня.** Вертикально двигает только подъёмник. Сам поршень
  остаётся горизонтальным: у него направление хода и есть вариант `side`,
  а `MPConsumer` знает лишь четыре горизонтали.

## Проверено в игре

Работает на 1.22.7: поршень и верёвочный подъёмник питаются от ванильного
ветряка, блоки плавно перелетают в соседнюю клетку, содержимое сундуков
переезжает вместе с ними, стоящий сверху едет — в том числе вверх на подъёмнике,
— а оказавшийся на пути отодвигается.

Быстрая проверка после изменений:

1. `/giveblock mechworks:piston-north`, поставить, подвести вал **сбоку**.
   Загрузить балки правым кликом (`game:supportbeam-*`).
2. В подсказке блока растёт `Speed` и `Charge`.
3. Положить перед поршнем цепочку из 3–4 блоков — уезжает целиком и плавно.
4. Сундук с вещами в середине цепочки — содержимое на месте после переезда.
5. Упереть цепочку в стену — не двигается вообще, ничего не ломается.
6. Встать на цепочку — едет вместе с ней, ровно на одну клетку, без провала
   внутрь блоков. Пройтись по ней во время хода — не сбрасывает.
7. Встать перед цепочкой — отодвигает. Идти ей навстречу — не вязнет.
8. Встать между цепочкой и стеной — прижимает вплотную, внутрь стены не загоняет.

Подъёмник:

9. `/giveblock mechworks:ropehoist-north`, вал сзади, под ним через воздух блок —
   едет вверх. Правый клик — едет вниз.
10. Груз дошёл до подъёмника — останавливается, не вбивается в него.
11. Встать на поднимаемый блок и **прокатиться несколько циклов подряд** вверх и
    вниз. Именно многократность важна: сбои тут проявлялись раз в несколько ходов.

Клей:

12. `/giveitem mechworks:glue`, склеить блоки — подсветка появляется, счётчик в
    чате растёт. Проверить **ровно два** блока: это был отдельный баг.
13. Склеить платформу 2x2, поднять подъёмником, прокатиться на ней.
14. Сломать блок из середины склеенной группы — машина должна двигать остаток,
    а не вставать намертво.
15. Перезайти в мир — клей на месте.

Платформа:

16. `/giveblock mechworks:turntable`, вал снизу, сверху склеенная конструкция —
    плавно поворачивается на четверть за ход, коротким путём. Вал сверху — в
    другую сторону.
17. **Направленный блок** (лестница) — после поворота смотрит на 90° в сторону,
    форма конструкции сохранена. Это проверка пары «позиция ↔ код блока».
18. Встать на платформу, особенно **у края** большой конструкции — везёт по дуге.
19. Препятствие в конечной клетке — поворот не происходит.

## Заметка на будущее

Три падения в игре подряд были вызваны одним и тем же: имя API взято по памяти,
а не из кода. `mechPartShape`, наследование от `BlockMPBase`, сэмплер `"tex"` —
каждый раз ответ лежал в исходниках VSSurvivalMod или Vintage Kinematics.

Для проверки имён есть `apidump` (см. историю разработки): читает метаданные
прямо из игровых DLL, потому что `VintagestoryAPI.xml` документирует не всё.
